# Ручна резервна копія Stage Base на Supabase Free

Повний резерв містить зашифрований архів PostgreSQL, окремий експорт ролей без паролів, копію файлів Storage та контрольні суми. Дамп включає всі доступні схеми проєкту, зокрема `auth`, `storage`, `supabase_migrations` і приватні схеми Stage Base. У ньому зберігаються функції, тригери, RLS та гранти. Дані Auth, включно з хешами паролів, потребують захисту на рівні інших секретів.

## Доступ і створення

1. У Supabase Dashboard відкрийте Stage-base → **Connect** → **Session pooler**. За наявності IPv6 можна використати Direct Connection. Для дампа потрібне підключення з правами читання всіх схем і даних. Використовуйте PostgreSQL client 17 для чинного PostgreSQL 17. Transaction pooler для цієї процедури не використовуйте.
2. На довіреному пристрої створіть приватні конфігурації libpq. У файлі сервісів із правами `0600` задайте секцію `[stage_base_backup]`, хост, порт, користувача і базу з Dashboard. Увімкніть `sslmode=verify-full` із довіреним сертифікатом у `sslrootcert`. Пароль збережіть у файлі `PGPASSFILE` із правами `0600`. Передайте утилітам лише шляхи `PGSERVICEFILE`, `PGPASSFILE` і назву `PGSERVICE=stage_base_backup`. Пароль не надсилайте в чат і не додавайте до URI в командному рядку.
3. Перевірте рядки `storage.buckets` і `storage.objects`. За наявності об’єктів скопіюйте кожен бакет у приватну локальну теку під його оригінальною назвою. Для масового копіювання скористайтеся Supabase Storage S3 і приватною конфігурацією rclone. Звірте кількість, розмір і контрольні суми, де вони доступні. Для порожнього Storage використайте порожню теку. Конфігурація бакетів зберігається в дампі PostgreSQL. Для узгодженості робіть резерв у вікно без запису файлів і бази або повторно звірте зміни в кінці.
4. Імпортуйте перевірений публічний GPG-ключ одержувача. Приватний ключ зберігайте окремо від резерву. Запустіть `tools/backup/manual-backup.sh ПОВНИЙ_ВІДБИТОК_КЛЮЧА /приватна/нова-тека /приватна/копія-storage`. Зберігайте результат у приватному сховищі поза GitHub. Перевірте `sha256sum -c SHA256SUMS`.
5. Обмежте доступ до резерву. Сплануйте ручні копії перед міграціями та за графіком команди. Зафіксуйте час, відповідального, перевірені контрольні суми й результати відновлення.

Експорт ролей не переносить паролі PostgreSQL. Він також не замінює окремий захищений опис налаштувань Supabase Auth, провайдерів, SMTP, Auth hooks, Edge Functions і секретів. Відновлюйте ці налаштування через захищену конфігурацію. Сесії після відновлення перевіряються окремо, за необхідності користувачі входять повторно.

## Відновлення

1. Перевірте контрольні суми. Використайте окремий локальний PostgreSQL/Supabase сумісної версії. Підготуйте потрібні розширення й ролі до відновлення. На керованому Supabase перегляньте експорт ролей і перенесіть лише потрібні користувацькі ролі та членство. Платформними ролями керує Supabase.
2. Перевірте вміст командою `gpg --decrypt database.dump.gpg | pg_restore --list`. Відновіть у підготовлену ізольовану БД через `gpg --decrypt database.dump.gpg | pg_restore --exit-on-error --single-transaction --dbname=stage_restore`. Для перевірки повного дампа використовуйте чисту ізольовану БД із доступними залежностями. Для підготовленого Supabase використовуйте вибірковий список `pg_restore --use-list` після звірки платформних схем.
3. Розпакуйте архів Storage у приватну теку. Перенесіть об’єкти через Storage API або S3 з тим самим шляхом. Використайте підтримувану процедурою відновлення синхронізацію метаданих, щоб не створити дублікати в `storage.objects`.
4. Зіставте кількості записів, міграції, користувацькі ролі, гранти, політики, функції та тригери. Перевірте вхід із тестовим акаунтом, приватний доступ до файлів і ключові операції Stage Base. Зафіксуйте час і результат. Робочий проєкт перемикайте лише після погодження.
