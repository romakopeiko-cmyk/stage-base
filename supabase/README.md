# SQL Stage Base

`applied-history/` містить SQL із шести записів `supabase_migrations.schema_migrations` чинного проєкту. Ці зміни вже застосовано до робочої бази. Файли залежать від базової схеми, створеної до цих записів, тому каталог слугує джерелом для звірки.

Перед відтворенням середовища потрібно отримати перевірений DDL базової схеми, включно з політиками, грантами, функціями, тригерами та конфігурацією приватних бакетів. Дані, секрети Auth та ключі залишаються у захищеному середовищі. SQL зі старої гілки `stagebase-backend` описує іншу структуру.

## Нові міграції

`migrations/` містить заплановані зміни до чинної схеми. Міграція центру сповіщень надає активному співробітнику читання власних повідомлень і право один раз позначити повідомлення прочитаним. Дату встановлює база. Створення повідомлень і надсилання пошти підключаються до серверних операцій окремо.

Порядок публікації центру сповіщень: застосувати перевірену міграцію до робочої схеми через Supabase, підтвердити наявність запису в історії та перевірити права, потім опублікувати клієнт. Для відкату клієнта достатньо попередньої версії GitHub Pages. Повідомлення і відмітки прочитання залишаються в базі.

## План відновлення

До першої операційної публікації перевірити доступність резервних копій на чинному тарифі. Узгодити відповідального, періодичність і місце зберігання зашифрованих копій. Резервувати схему й дані Postgres, окремо приватні файли Storage та документувати серверну конфігурацію, шаблони листів і залежності. Копії зберігати поза публічним GitHub.

Відпрацювати відновлення в ізольованому середовищі: відновити БД і файли, звірити кількість записів та контрольні суми файлів, перевірити вхід, доступ за ролями, історію й відповідність об’єктів метаданим. Зафіксувати час відновлення та останню доступну точку даних. Після інциденту перемикати клієнт лише після звірки й перевірки прав доступу.
